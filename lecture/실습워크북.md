스택 2개, 리소스 12개입니다. 그리고 오늘 다루는 것은 그 리소스가 아니라 `terraform.tfstate` 파일 하나가 어디에 있는지입니다.

| 스택 | 만드는 것 | 개수 | 이 스택의 state는 |
|------|----------|------|----------------|
| `practice/bootstrap/` | S3 버킷 + 버전 관리 + 암호화 + 퍼블릭 차단 + DynamoDB 테이블 | **5** | **로컬** (오늘도, 7주차까지도) |
| `practice/app/` | VPC + subnet + IGW + route table + 연결 + SG + EC2 | **7** | **로컬에서 S3로 이사** |

> [!CAUTION]
> **비용.** app 스택을 apply하면 시간당 $0.019가 붙습니다. destroy를 잊고 한 달 두면 약 $13.87입니다. Block C는 선택이 아닙니다.

> **올리면 안 되는 값.** 본인 공인 IP · AWS 계정번호 12자리 · 액세스 키 · `terraform.tfvars` · `terraform.tfstate` · `state.json` · `.pem` 파일. 마스킹 명령은 C-4에 있습니다.

> [!IMPORTANT]
> **작업 폴더가 오늘은 둘입니다.** `practice/bootstrap/`과 `practice/app/`. 오늘 자주 나는 사고가 엉뚱한 폴더에서 명령을 치는 것입니다.
> 이 문서의 코드블록 첫 줄에 붙은 `# pwd == ...` 주석은 **그 블록의 명령을 다 친 뒤에 있어야 하는 위치**입니다. 블록 안에 `cd`가 있으면 시작 위치는 그 위 블록의 값입니다. 매 블록 끝에 `pwd`로 대조하세요.

## 오늘의 지도: state가 사는 곳

week1의 지도는 명령의 흐름, week2의 지도는 리소스 사이의 참조였습니다. 오늘의 지도는 파일 하나가 사는 곳입니다.

이 지도를 한 세션에 세 번 씁니다. Block A에서 저장소를 만들고, Block B에서 옮기고, Block C에서 역순으로 정리합니다.

### ① BEFORE: 오늘 시작 시점 (= week2가 끝난 상태)

```
        내 노트북                                  AWS 계정 (서울)
 ┌──────────────────────────────┐           ┌──────────────────────────┐
 │  practice/app/               │   apply   │   VPC · subnet · IGW     │
 │    *.tf                      │ ────────> │   route table · 연결     │
 │    terraform.tfstate  ◀ state│           │   security group · EC2   │
 │       평문 JSON              │           └──────────────────────────┘
 │       나만 볼 수 있습니다    │
 │       잠금이 없습니다        │
 └──────────────────────────────┘
```

### ② AFTER: 오늘 끝날 때

```
        내 노트북                        AWS 계정 (서울)
 ┌──────────────────────┐   ┌────────────────────────────────────────────┐
 │ practice/app/        │   │  S3  {project}-tfstate                     │
 │   *.tf               │   │   └─ week03/app/terraform.tfstate  ◀ state │
 │   backend.tf ────────┼──>│        버전 관리 ON · SSE ON · 퍼블릭 차단 │
 │     bucket / key     │   │                                            │
 │     region / encrypt │   │  DynamoDB  {project}-tflock                │
 │     dynamodb_table   │   │   └─ LockID 항목: apply 중에만 1개         │
 │                      │   └───────────────────┬────────────────────────┘
 │   terraform.tfstate  │                       │ apply
 │     ▲ 크기가 확 줄었습니다                   ▼
 │   terraform.tfstate.backup        ┌──────────────────────────┐
 │     ▲ 옮기기 전 내용이 남습니다   │  VPC 5 · SG · EC2        │
 └──────────────────────┘            └──────────────────────────┘
```

> **읽는 법:** 새로 생긴 참조는 하나뿐입니다. `backend.tf`에서 S3로 향하는 것입니다. 그리고 `network.tf`와 `compute.tf`는 한 글자도 바뀌지 않았습니다.

### ③ 스택 경계선: 여기에는 참조가 없습니다

```
 ┌─────────────── bootstrap 스택 ────────────────┐
 │  backend : local ← 여기는 원격화하지 않습니다 │
 │  state   : 내 노트북의 terraform.tfstate      │
 │                                               │
 │  만드는 것 (5)                                │
 │    aws_s3_bucket.tfstate                      │
 │      ├─ _versioning                           │
 │      ├─ _server_side_encryption_configuration │
 │      └─ _public_access_block                  │
 │    aws_dynamodb_table.tflock                  │
 └───────────────────────┬───────────────────────┘
                         │  output backend_config 다섯 줄
              ╎╎╎╎╎╎╎╎╎╎╎╎╎╎╎╎╎╎╎╎╎╎╎╎╎   ← 점선은 코드 참조가 아닙니다
              ╎   사람이 손으로 복사     ╎      Terraform 은 이 선을 모릅니다
              ╎   (backend 는 변수 불가) ╎
              ╎╎╎╎╎╎╎╎╎╎╎╎╎╎╎╎╎╎╎╎╎╎╎╎╎
                         ▼
 ┌──────────────── app 스택 ─────────────────────┐
 │  backend : s3      ← 위 버킷을 쓴다           │
 │  state   : S3 의 week03/app/terraform.tfstate │
 │  만드는 것 (7): VPC · subnet · IGW ·          │
 │                 route table · 연결 · SG · EC2 │
 └───────────────────────────────────────────────┘

   생성 순서 :  bootstrap ───────────> app
   삭제 순서 :  app ───────────> bootstrap (7주차)
                                 ▲
                반대로 하면 state 저장소가 먼저 사라집니다.
                app 을 지울 수단이 없어집니다.  (C-5)
```

> [!IMPORTANT]
> week2에서는 참조 11개를 잇는 것만으로 순서가 만들어졌습니다. 이 점선 위에는 참조가 없습니다.
> 그래서 Terraform이 순서를 계산해주지 않고, 사람이 지켜야 합니다. 그리고 스택 사이에는 `depends_on`조차 쓸 수 없습니다.

### [실습] A-3. TODO ①~④: S3 버킷과 안전장치 셋

지금 하는 일은 state를 담을 버킷을 만들고, 거기에 버전 관리 · 암호화 · 퍼블릭 차단을 거는 것입니다.

`main.tf`를 열면 주석으로 된 힌트가 있습니다. 주석을 풀어 채우세요. 왜 버킷 하나로 끝나지 않는지는 개념워크북 Part 4에 있습니다.

①은 버킷입니다.

```hcl
resource "aws_s3_bucket" "tfstate" {
  bucket = "${var.project_name}-tfstate"

  tags = { Name = "${var.project_name}-tfstate" }
}
```

②는 버전 관리입니다. `bucket = aws_s3_bucket.tfstate.id`가 참조이고, 이 한 줄이 버킷을 먼저 만들게 합니다.

```hcl
resource "aws_s3_bucket_versioning" "tfstate" {
  bucket = aws_s3_bucket.tfstate.id

  versioning_configuration {
    status = "Enabled"
  }
}
```

③은 서버측 암호화입니다.

```hcl
resource "aws_s3_bucket_server_side_encryption_configuration" "tfstate" {
  bucket = aws_s3_bucket.tfstate.id

  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "AES256"
    }
  }
}
```

④는 퍼블릭 접근 차단입니다. 네 개 모두 `true`입니다.

```hcl
resource "aws_s3_bucket_public_access_block" "tfstate" {
  bucket = aws_s3_bucket.tfstate.id

  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}
```

> [!WARNING]
> `force_destroy`를 넣지 마세요. 켜면 `destroy` 한 번에 state 이력 전체가 사라져서 ②가 무의미해집니다. 개념워크북 13번.

### [실습] A-4. TODO ⑤~⑧: 잠금 테이블과 output

지금 하는 일은 잠금용 테이블을 만들고, app 스택에 넘길 값을 output으로 꺼내는 것입니다.

⑤는 DynamoDB 테이블입니다.

```hcl
resource "aws_dynamodb_table" "tflock" {
  name         = "${var.project_name}-tflock"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "LockID"

  attribute {
    name = "LockID"
    type = "S" # S = 문자열
  }

  tags = { Name = "${var.project_name}-tflock" }
}
```

> [!CAUTION]
> `billing_mode`는 `PAY_PER_REQUEST`여야 합니다. `PROVISIONED`로 두면 쓰지 않아도 과금됩니다.
>
> `hash_key`는 `LockID`여야 합니다. Terraform이 그 이름으로 찾기 때문에, 다른 이름을 쓰면 잠금이 동작하지 않습니다.

이제 `outputs.tf`의 ⑥ ⑦ ⑧을 채웁니다. 세 개 다 채우세요. A-6에서 ⑧의 출력을 복사해 B-4에 붙여 넣습니다.

```hcl
output "bucket_name" {
  description = "state를 담는 S3 버킷 이름. app/backend.tf 의 bucket 에 그대로 넣습니다"
  value       = aws_s3_bucket.tfstate.id
}

output "table_name" {
  description = "잠금용 DynamoDB 테이블 이름. app/backend.tf 의 dynamodb_table 에 넣습니다"
  value       = aws_dynamodb_table.tflock.name
}

output "backend_config" {
  description = "app/backend.tf 의 backend \"s3\" 블록 안에 붙여 넣을 값 다섯 줄"
  value       = <<-EOT
    bucket         = "${aws_s3_bucket.tfstate.id}"
    key            = "week03/app/terraform.tfstate"
    region         = "${var.region}"
    dynamodb_table = "${aws_dynamodb_table.tflock.name}"
    encrypt        = true
  EOT
}
```

> [!TIP]
> ⑧이 오늘 실습의 안전장치입니다. 손으로 옮겨 적다가 버킷 이름을 틀리면 B-5의 `init`이 `NoSuchBucket`으로 죽습니다. 여기서는 `${}` 보간을 쓸 수 있는데 backend 블록 안에서는 못 쓴다는 것도 같이 보세요. 개념워크북 4번.

## Block B. 각자 진행 (20분): app을 원격으로 옮기기

`practice/app/`의 `network.tf`와 `compute.tf`는 week2 정답 코드와 같습니다. 오늘은 채우지 않고 읽기만 합니다. 여기서 손으로 만드는 것은 `terraform.tfvars`와 `backend.tf`뿐입니다.

순서가 이 블록의 핵심입니다. 먼저 로컬 state로 만들고, 그다음 옮깁니다. 처음부터 backend를 켜면 옮길 state가 없어서 오늘의 주제를 볼 수 없습니다. 개념워크북 5번.

### [실습] B-1. 내 값 채우기

지금 하는 일은 app 스택의 변수를 채우는 것입니다.

```hcl
project_name  = "boaz26-w3-kdh1834"

instance_type = "t3.micro"
```

### [실습] B-4. `backend.tf` 주석을 풀고 값 붙여넣기

지금 하는 일은 state를 어디에 둘지 코드에 적는 것입니다.

`backend.tf`를 열어 아래쪽 주석 블록의 `#`을 지우고, `bucket`과 `dynamodb_table`을 A-6의 출력으로 바꾸세요.

```hcl
terraform {
  backend "s3" {
    bucket         = "boaz26-w3-kdh1834-tfstate"
    key            = "week03/app/terraform.tfstate"
    region         = "ap-northeast-2"
    dynamodb_table = "boaz26-w3-kdh1834-tflock"
    encrypt        = true
  }
}
```

> [!WARNING]
> 버킷 이름 한 글자만 틀려도 다음 단계의 `init`이 실패합니다. A-6의 `terraform output -raw backend_config` 출력을 복사해 붙이세요.

[함정] 여기에 `var.project_name`을 쓰고 싶어질 텐데 안 됩니다. `init`은 backend를 가장 먼저 초기화하고 그 시점에는 변수가 아직 평가되지 않았습니다. 개념워크북 4번.

### [개념] C-5. bootstrap 스택을 지우는 절차 (이번 주에는 실행하지 않습니다)

지금 읽는 것은 7주차에 쓸 절차입니다. 이번 주에는 실행하지 않습니다.

> [!WARNING]
> 지금 실행하면 4주차부터 7주차까지 쓸 state 저장소가 사라집니다. 이 절에는 7주차에 쓸 절차만 적어둡니다. 읽고 넘어가세요.

`force_destroy`를 끄고 버전 관리를 켜 뒀기 때문에 `terraform destroy`만으로는 `BucketNotEmpty`로 실패합니다. `aws s3 rm --recursive`로도 구버전이 남습니다. 방법이 두 가지입니다.

Terraform으로 하는 쪽이 간단합니다. `aws_s3_bucket.tfstate`에 `force_destroy = true`를 넣고 `apply`한 다음 `destroy`합니다.

```bash
# 7주차에만. bootstrap/main.tf 에 force_destroy = true 추가 후
terraform apply
terraform destroy
```

CLI로 직접 비우려면 버전과 삭제 마커를 각각 지워야 합니다.

```bash
# 7주차에만
B="boaz26-w3-kdh1834-tfstate"

aws s3api list-object-versions --bucket "$B" \
  --query '{Objects: Versions[].{Key:Key,VersionId:VersionId}}' \
  --output json > versions.json
aws s3api delete-objects --bucket "$B" --delete file://versions.json

aws s3api list-object-versions --bucket "$B" \
  --query '{Objects: DeleteMarkers[].{Key:Key,VersionId:VersionId}}' \
  --output json > markers.json
aws s3api delete-objects --bucket "$B" --delete file://markers.json

terraform destroy
```

목록이 비어 있으면 `{"Objects": null}`이 나오고 `delete-objects`가 인자 검증에서 실패합니다. 그 경우 그 호출은 건너뛰세요. `delete-objects`는 한 번에 1000개까지 받습니다.

## 부록. 트러블슈팅

| 증상 | 원인 | 해결 |
|------|------|------|
| `plan`이 `project_name`을 물어봄 | `terraform.tfvars` 없음 | `cp example.tfvars terraform.tfvars` 후 값 채우기 |
| `InvalidBucketName` | `project_name`에 대문자 | 소문자·숫자·하이픈만 |
| `BucketAlreadyExists` | 남이 쓰는 이름 | `project_name`에 본인 GitHub ID 넣기 |
| `NoSuchBucket` on `init` | backend의 버킷 이름 오타 | A-6 출력과 대조 |
| `AccessDenied` on `init` | IAM 권한 부족 | 개념워크북 Part 3의 권한 목록 |
| migrate 후 `7 to add` | state가 안 옮겨짐 | 멈추고 질문. apply 금지 |
| `Error acquiring the state lock` | 잠금이 남음 | 아무도 작업 안 하는 것 확인 후 `force-unlock` |
| backend에 `var.` 못 씀 | init 시점에 변수 미평가 | 값 직접 입력 또는 `-backend-config` |
| `destroy`가 SG/서브넷에서 멈춤 | ENI 잔존 | 잠시 후 재실행 |
| `Warning: Deprecated Parameter` | `dynamodb_table` 사용 | 정상입니다. 개념워크북 9번 |
